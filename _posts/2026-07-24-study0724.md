## 간단한 용어 정리
 
* 정수 오버플로우
  정수 연산의 결과가 타입이 표현 가능한 범위를 벗어나서 순환 되는 현상.
* 타입 혼동
  메모리 데이터를 실제 타입과 다른 잘못된 타입으로 해석해서 사용하는 문제(실제 데이터와 다른 잘못된 구조체로 선언해 이상한 오프셋에 접근)
  (signedness confusion 타입 혼동의 하위 장르, unsigned를 signed로 해석해 사용, 혹은 그 반대.)
* 절단 
  넓은 타입 값을 좁은 타입에 저장하면서 상위 비트가 손실되는 문제.

## 오버플로 예시 - Stagefright(CVE-2015-1538)

안드로이드의 미디어를 파싱하는 함수가 정수 오버플로우 취약점으로, 임의 코드 실행이 가능했던 오류

1. 취약점이 있는 함수는 ESDS라는 컨테이너속의 명세를 파싱하는 코드였음

``` c++
if (streamDependenceFlag) {
    offset += 2;
    size -= 2;              // size < 2 인지 확인 안 함
}
if (URLlength >= size) {
    offset += URLlength + 1;
    size -= URLlength + 1;  // 마찬가지로 검증 없음
}
if (OCRstreamFlag) {
    offset += 2;
    size -= 2;              // 마찬가지
}
```
2. 반복문 내부에서 size를 감소 시켜가면서 그 위치에서 차례로 파싱 실시
3. size가 unsigned  && 검증 로직 없으 => 언더 플로를 일으키게 적당한 값을 넣어 메모리 임의 주소 코드 실행
[참고 보고서](https://dash.harvard.edu/server/api/core/bitstreams/8efa6308-aac2-43e0-91cf-aed9ef10e6b4/content)



## 절단 예시 - ping of death

``` c++
q = fp->ipq_frags;
ip = GETIP(q);
// if (next + (ip->ip_hl << 2) > IP_MAXPACKET) {
IPSTAT_INC(ips_toolong);
IPSTAT_ADD(ips_fragdropped, fp->ipq_nfrags);
ip_freef(head, fp);
goto done;
// }
//주석 처리된 부분이 현재의 ip 패킷 처리 코드
```

* ip->ip_hl << 2 -> 4x 헤더 길이 필드 = 헤더길이(32비트)
* next -> ip 페이로드 길이 (32비트)
1. 둘을 더하면 ip 패킷의 크기. 근데 더해진 결과를 16비트에 저장. 
2. 이를 16비트에 저장하면 => 상위 비트가 절단. 실제보다 작은 절단된 공간을 할당받음. 
3. 절단되지 않았다 생각하고 할당 받은 부분 뒤쪽을 처리하려다가(OOB) -> 크래시 발생



## 타입 혼동 예시 - CVE-2023-36802

1. 윈도우의 커널 드라이브 중  FindObject()는 타입 검증 없이  FSStreamReg구조체를 반환한다 가정
2. 근데 해당 함수는 더 작은 크기의 FSContextReg구조체를 반환할수도 있었음
3. 만약 함수가 FSStreamReg구조체로 착각해 FSStreamReg 구조체의 외부 영역을 읽고 쓰려할 수 있음.



## 정적 탐지를 어떻게할까? 난이도는?

* **절단**(쉬움) ->  
넓은 산술연산을 더 좁은 곳으로 할당하는 경우를 정적탐지 (형변환 연산 중 해당하는 경우를 탐지 후 오탐 처리만 해주면됨)
* **정수 오버플로**(중간) ->    
  해당 연산의 지배블록(반드시 연산보다 선행되는 블록)에 검사 패턴(CBRANCH=나 분기해요 , INT_LESS... = 비교 연산)이 있는지 검사  
  +오염분석을 통해서 오탐 처리  
  +경로 민감 분석 (SMT) 실행시 정밀도 크게 늚. (비용은 쫌 있음)  
* **타입 혼동**(매우 어려움) ->  
  타입과 실제 포인터가 가리키는 메모리에 있는 값이 같은가를 묻는 것 -> 정적에선 힘듬  
  거기다 역공학관점에서는 구조체 정보도 다날아가서, 추정한것이므로 더 부정확.   
  기껏해야 리턴타입이 작은 구조체인 함수 발견 ->  검증없이 매우 큰 오프셋으로 리턴 주소에 접근하는걸 패턴 매칭으로 잡아내는 정도.

## 왜 결국 유사 패턴 매칭인가**  

1. 위의 취약점들은 런타임에 들어오는 값들에 의존하여 발생 -> 실행 없이 맞추는 것은 한계.
2. 그래서 정적으로 최대한 엄밀하게 하고자 한게 언급된 Symbolic excution, SMT...
3. but, 이 방법은 가능한 경로들을 다가보는 것이라서 경로 폭발이 일어남.
4. 패턴매칭을 통해 싸게 후보를 뽑고, 국지적으로 저 분석들을 실행하는 것.
