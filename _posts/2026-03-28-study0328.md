# 처음의 방향성  

로고페일 관련한 보고서중
[해당](https://www.binarly.io/advisories/brly-logofail-2023-007) 보고서의 내용이 탐지해볼만 할것같아서 해당 드라이버의 취약점 부분을 탐지 가능한 기드라 스크립트를 작성하고자 하였다.  

일단 해당 드라이버의 취약점을 잡고 -> 추가적이 보고서의 내용을 잡고... 이렇게 개선해나갈 예정이었다.  

# 실제 드라이버에서는 어떤 어려움이 있었나?  

**1.** 너무 커다란 구조, 관련없는 부분들과 복잡하게 얽힌 호출관계로 메인로직 찾기조차 힘듬 

기드라 리스팅에는 따로 high pcode로 출력하는 기능이 없고, 스크립트를 만들어 따로 출력해도 파악이 힘드니, 
기드라 자체의 그래프로 그려주는 기능을 애용하고있다. 근데 이 문제가 있는 함수를 직접 해보면..
![](/postPic/26-03-29/6.png)  
이렇게 된다. (저 작은 붉은점 하나하나가 바노드와 opcode들이다..)
그래서 실제 문제와 관련된 p코드를 파악하는데되 굉장히 긴시간이 걸렸다.

**2.** 메인 로직을 잡아도 문제가 해결되지 않을 수 있음.

Q. 그러면 어디서 초기화 되었을까?

# 그러면 실제 드라이버를 활용하는 것은 아예 쓸모 없는가?  

그렇진 않았다. 실제 탐지 스크립트를 완성한다면, 실행해보며, 예상 못한 케이스 지만, 나의 탐지로직과 관련한 허점을 여럿 찾을 수 있었다.   
![](/postPic/26-03-29/11.png)  
여기보면 uVar9에 위험한 연산이 저장되었다.  
uVar5와 uVar6는 크기검사가 되었을까?  
단순히 if문으로 변수의 검사 여부만 살핀다면 검사되지 않았다.  
하지만 if 문을 자세히 살펴보면 uVar5,6에 담긴 값을 그대로 비교해서 살피는 모습이다.  
=> 검사가 된 오탐이다.

# 어떻게 방향성을 수정했는가.

기존 : 실제 CVE 속 드라이버의 취약점을 탐지가능한 스크립트를 작성한다.  
개선 : 
* CVE 리포트 속 취약점의 메인 로직을 탐지할 수있는 스크립트를 작성한다.  
* CVE 리포트 속 핵심 부분이 모두 구현된 자체제작 드라이버로 테스트를 한다.
* (바램)동일 CVE 타 사례로 확장가능하다면 적용시켜 더욱 제너럴하기 + 테스트 데이터 확보

Q. 실제 취약점 드라이버에서의 탐색이 불가능하다면 의미 없는 것이 아닌가?  
A.  
* 해당 CVE와 동일한 취약점을 탐색하나, 탐지가능한 범위가 ~~인 스크립트를 제작할 것. 모든 관련 CVE를 탐지하려한다면, 범위도 제각각일 것이고, 난이도와 신뢰성도 급락할 것이다. 
또한 상용도구들도 복잡도별 할수있는게 제각각이니 개발 상황에 맞게 잘골라 써야한다 => 상용도구들도 만능이아니다!  

* 또한, 위에 설명한 어려움들은 상용도구에서도 어려운 문제라고 함.  

=> 불가능해보이는 부분은 최대한 패턴매칭을 활용해 쉽게 하거나 스코프에서 제외시키는게 오히려 실용적.
